> 经验声明：本文是 AI 编程协作系列里正式进入 Memory 的第一篇。前面几篇讲了 Rules、Skills、渐进式披露和项目 Map，这一篇不重点讲产品，而是讲为什么 AI 协作需要一个长期记忆层。

前面几篇文章一直在讲同一个问题：

AI 编程工具想在真实项目里稳定工作，不能只靠模型本身。

它至少需要几层外部结构：

- Rules：告诉 AI 哪些边界不能踩。
- Skills：告诉 AI 复杂任务应该怎么推进。
- Project Map：告诉 AI 当前任务应该先去哪里找。
- Memory：让 AI 能在需要时找回过去发生过的事情。

这篇要讲的是最后一层：Memory。

更准确地说，是为什么真实项目里的 AI 协作，不能只停留在“当前会话”和“当前上下文”里。

## 剩下的问题是什么

如果前面已经有了 Rules、Skills 和 Project Map，为什么还需要 Memory？

因为它们解决的问题不一样。

Rules 解决的是：

```text
以后每次都必须遵守什么？
```

Skills 解决的是：

```text
遇到某类任务时，应该按什么流程做？
```

Project Map 解决的是：

```text
当前任务应该先去哪里找？
```

但真实项目里还有一类信息，不完全属于这三者。

它们是过去发生过的事情、历史决策、业务背景、踩坑记录、字段含义、线上问题复盘。

这些信息不一定每次都要出现。

但当任务相关时，它们必须能被找回来。

这就是 Memory 要解决的问题：

```text
过去发生过、未来可能有用的项目背景，如何被保存，并在正确时机被取回？
```

## Memory 不是 Rule

这里最容易混的是 Memory 和 Rule。

比如这句话：

```text
接口错误不能在业务组件里直接弹 toast，必须走统一 errorHandler。
```

这更像 Rule。

因为它是稳定约束，AI 每次改接口调用时都应该遵守。

但下面这类信息就不一样：

```text
上次用户资料页保存失败，是因为 token 刷新和资料保存请求同时发起，导致后端拿到了旧 token。
```

这不是一条每次都要常驻的规则。

它是一段历史背景。

平时不需要放进上下文。

但如果下次又遇到“用户资料页保存失败”“token 刷新”“接口偶发 401”，这段记忆就很有价值。

所以我更愿意这样区分：

```text
Rule 是必须持续生效的约束。
Memory 是未来某些任务可能需要取回的历史背景。
```

Rule 太少，AI 会乱来。

Memory 太少，AI 会重复踩坑。

Rule 太多，会污染上下文。

Memory 如果不能按需检索，也会变成另一个上下文垃圾桶。

## Memory 也不是把上下文变长

很多人一听 Memory，会想到更长的上下文窗口。

但我不认为问题应该这样解决。

上下文窗口再大，也不应该把所有历史内容每次都塞进去。

因为这会带来三个问题：

1. 成本高。
2. 噪音大。
3. 当前任务的重点会被冲淡。

真正需要的不是“无限长上下文”，而是“可检索上下文”。

也就是说：

```text
当前任务需要什么，就取回什么。
```

如果你在改登录页，AI 不需要知道整个项目所有历史决策。

它只需要知道和登录、认证、接口错误、表单校验相关的记忆。

Memory 的价值不在于保存一切，而在于能在正确时机找回正确的东西。

这和前面讲的渐进式披露是一回事。

## 一个更真实的例子

假设你对 AI 说：

```text
用户资料页保存失败，帮我看一下。
```

如果只有当前上下文，AI 可能会先看表单代码、接口参数、请求日志。

这些当然都应该看。

但真实项目里，问题可能和过去发生过的事情有关。

比如长期记忆里有三条相关记录：

```text
用户资料页曾经因为 token 刷新时序导致保存接口偶发 401。

profile.status = 2 表示账号冻结，不是普通保存失败。

资料保存接口的错误提示统一由 requestErrorHandler 处理，业务组件不要重复 toast。
```

这三条信息的性质并不一样。

第一条是历史 Bug。

第二条是业务字段含义。

第三条更接近项目 Rule。

当 AI 能把它们按需取回来时，排查路径会完全不同。

它不会只盯着表单校验。

它会知道还要检查 token 刷新时序、字段业务含义，以及错误处理边界。

这就是长期记忆层的实际价值：

**不是让 AI 记住更多，而是让它少重复从零开始。**

## 什么信息适合进入 Memory

不是所有东西都应该进入 Memory。

我认为适合保存的，通常是这些内容：

- 业务字段含义。
- 历史 Bug 和处理结论。
- 模块设计原因。
- 线上事故复盘。
- 用户长期偏好。
- 项目里的隐性约定。
- 数据库表和字段说明。
- 某次技术选择背后的取舍。

这些信息有一个共同点：

它们不是每次都要强制进入上下文，但未来很可能在某些任务里再次有用。

所以它们不适合全部写进 Rule。

也不适合只留在某一次聊天记录里。

它们需要被保存、索引、检索，并在任务相关时重新进入 Context。

## 什么信息不适合进入 Memory

Memory 也不能什么都收。

否则它会变成另一个垃圾桶。

我认为这些内容不适合随便放进长期记忆：

- 一次性的临时任务描述。
- 已经过期的排查猜测。
- 没有验证过的模型推断。
- 和项目无关的闲聊。
- 可以从代码里稳定读取到的事实。
- 必须每次遵守的红线。

最后一类更适合放进 Rule。

比如：

```text
删除线上数据前必须先询问用户。
```

这不应该等检索到了才生效。

它应该是常驻红线。

所以 Memory 的设计重点不是“记得越多越好”，而是“什么值得记，什么时候取回，取回后怎么使用”。

## 为什么是语义检索

项目经验很多时候不是关键词能完全匹配的。

你这次问的是：

```text
保存用户资料失败怎么处理？
```

但历史记忆里可能写的是：

```text
profile update 接口曾经因为 refreshToken 时序导致偶发 401。
```

这两句话没有太多相同关键词，但语义上可能高度相关。

所以 Memory 不应该只是简单全文搜索。

它至少应该支持语义检索。

这也是我会考虑向量数据库的原因。

不是因为“向量”这个词高级，而是因为真实项目里的历史经验往往换一种说法就找不到了。

长期记忆如果找不回来，就等于没有。

## 为什么要本地优先

长期记忆里很容易包含敏感信息。

比如：

- 私有项目结构。
- 内部接口字段。
- 业务规则。
- 用户偏好。
- 历史问题复盘。
- 数据库 schema。

这些东西不一定适合默认上传到远端服务。

所以我更倾向于让第一层 Memory 先本地优先。

本地优先不是说永远不能同步。

而是默认控制权应该在开发者和团队手里。

AI 协作要真正进入日常工程，长期记忆就不能只是某个远端聊天产品里的附属功能。

它更应该像代码、配置、数据库、日志一样，成为开发者可以理解、迁移、备份和审计的基础设施。

## 为什么需要协议化

Memory 如果只能服务一个工具，价值会被限制。

今天你可能用 Cursor。

明天你可能用 Claude Code。

后天你可能用 Codex。

如果每个工具都要单独适配一套记忆系统，长期上下文就会继续碎片化。

所以 Memory 不只需要保存和检索，也需要一套通用访问方式。

这就是 MCP 这类协议有价值的地方。

Memory 本身要外部化。

访问 Memory 的方式也要协议化。

否则你只是把“记忆困在聊天窗口里”，换成了“记忆困在某一个工具里”。

## Elephance 只是这个理念的一个实现

在这个背景下，我做了 [Elephance](https://github.com/l1uqi/elephance)。

但对我来说，产品不是重点。

重点是这个理念：

```text
AI 编程工具需要一个本地优先、可检索、可协议化接入的长期记忆层。
```

Elephance 只是我对这个理念的一个实现尝试。

它目前主要包括两部分：

- `@elephance/core`：核心 SDK，负责记忆和 schema 的存储、查询等能力。
- `@elephance/mcp`：MCP Server，让支持 MCP 的 AI 客户端可以调用这些能力。

底层使用 LanceDB 做本地向量存储。

对外暴露的能力围绕两类展开：

- Memory：保存和查询长期记忆。
- Schema：保存和查询项目结构、字段、表等信息。

比如：

```text
memory_upsert
memory_query
schema_replace_source
schema_query
```

这些接口本身不复杂。

真正重要的是它们背后的协作方式：

**AI 不应该每次都重新认识你的项目。**

## 这和前几篇文章如何连起来

到这里，前几篇文章其实可以连成一条完整路径。

Rules 解决的是：

```text
AI 必须遵守什么？
```

Skills 解决的是：

```text
复杂任务应该按什么流程做？
```

Project Map 解决的是：

```text
AI 应该先去哪里找？
```

Memory 解决的是：

```text
过去沉淀下来的项目背景，如何在需要时被找回？
```

这四者不是互相替代的关系。

它们应该协同工作。

一个更理想的流程是：

1. AI 先读 Project Map，判断当前任务涉及用户模块。
2. 进入接口修改场景后，触发对应 Rule。
3. 如果任务需要缺陷流转，打开对应 Skill。
4. 如果涉及历史字段含义或之前踩过的坑，再查询 Memory。

这才是我理解的 AI 工程协作基础设施。

## 我看论文时被确认的部分

后来我看到一篇论文：[Externalization in LLM Agents: A Unified Review of Memory, Skills, Protocols and Harness Engineering](https://arxiv.org/abs/2604.08224)，arXiv:2604.08224。

这篇论文里有一个方向和我的感受很接近：

现在很多 Agent 能力的提升，并不只是来自模型权重本身，而是来自模型外部运行环境的重新组织。

也就是说，Agent 不是只靠“脑子更聪明”变强。

它也会通过外部结构变强：

- Memory 把状态外部化。
- Skills 把流程经验外部化。
- Protocols 把交互结构外部化。
- Harness 把这些东西组织成可执行系统。

Rules、Skills、Project Map、Memory，本质上都是在帮 AI 把原本需要临时猜、临时记、临时组织的东西，变成外部可复用的结构。

下面这张图来自这篇论文，正好解释了 Memory 在 Agent 系统中的位置。

![Memory as Externalized Agent State](/img/elephance/externalized-memory.jpg)

这部分对我来说不是起点，而是确认：

AI 协作变强，不只是换更强模型，也是在模型外部建立更好的记忆、流程、协议和运行环境。

## 总结

我现在越来越确定，真实项目里的 AI 协作不能只依赖当前会话。

模型负责推理和生成。

Rules 负责边界。

Skills 负责流程。

Project Map 负责导航。

Memory 负责长期背景。

长期记忆层的价值，不是保存一切，也不是把上下文无限拉长。

它真正要解决的是：

```text
过去发生过、未来可能有用的项目经验，如何在正确时机回到 AI 的 Context 里。
```

Elephance 只是这个理念的一个实现。

产品会变，工具会变，模型也会变。

但我认为这个方向不会变：

**AI 不应该每次都重新认识你的项目。**
