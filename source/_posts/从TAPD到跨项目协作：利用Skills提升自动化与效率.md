> 经验声明：以上心得和实践均来自我的真实项目开发经验。同时，本篇文章是在 Gemini 和 GPT-5.4 的协助下共同创作完成。配图由 Nano Banana 2 创作。

本文通过一个简单的例子聊聊 Skills 是什么、能做什么，以及它和其它工具的区别。更具体地说，我想分享如何利用 Skills 提升多项目之间的协作效率，以及如何把原本散落在 Rule 里的流程规则模块化，让跨项目管理变得更加灵活、高效。

![从 TAPD 到代码：模块化 Skills SOP 导航](/img/tapd-skills/tapd-skills-cover.png)

虽然在之前的文章中，我提到过我的项目里很少依赖 Skills，但这并不代表我从未使用过它们。

我想先抛出一个核心观点：**编码应当是模型自身的原生行为。**

换句话说，Skill 对纯编码能力的提升并不大，它更多是业务流程上的“方向性辅助”。如果一个 AI 还需要通过 Skill 来学习如何写逻辑或重构代码，那它显然还没达到一个合格“AI 程序员”的水准。在我的体系中，编码靠模型天赋，流程靠 Skill 导航。Skill 的存在，是为了让具备强大编码能力的模型，能够像“熟练工”一样精准对接 TAPD 空间、识别项目配置，并完成自动化闭环。

而真正决定项目执行效率和正确性的，往往是规则（Rule）本身。规则定义了业务流程的结构，也保证每个步骤都符合规范，它的重要性远超其它辅助工具。

MCP 和 Rule 在项目开发中各有核心价值：MCP 负责打破信息孤岛，让 AI 能实时感知上下文；Rule 负责沉淀流程规范，让需求管理和缺陷修复形成自动化闭环。而今天，我想继续往前走一步：**如何通过把这些规则进一步模块化成 Skills，提升多项目协作效率。**

随着项目规模不断增长，单纯依靠 Rule 的方案已经无法满足跨项目管理需求。Skills 的引入，让自动化管理变得更加灵活，也更容易复用。

## 回到 TAPD 到代码的自动化实践

在之前的讨论中，我们提到过如何通过 MCP 和 Rule 实现自动化、高效的开发实践。现在，我们进一步看 TAPD 如何与代码、需求和 Bug 管理紧密结合，尤其是如何将 TAPD 项目与空间 ID 绑定，以及如何通过 MCP 实现需求读取、Bug 修改、TAPD 联动等操作。

### 从 Rule 到 Skills 的调整

虽然上述示例通过 Rule 成功实现了 TAPD 与项目的紧密绑定，确保了需求和缺陷可以被自动化处理，但这种方法也有明显局限：**Rule 与项目强绑定，无法很好地支持多个项目之间的灵活复用。**

随着项目数量增加、团队协作方式变化，这种绑定方式会逐渐变得不够灵活。

### 现有缺点

#### Rule 与项目强绑定

当前的 Rule 配置与项目空间 ID（`workspace_id`）是强绑定的。这意味着每次需要在不同项目中实现相似规则时，都必须手动调整配置文件中的空间 ID。

当项目数量较多，或需求变化频繁时，这种做法会显得非常低效。例如，我们不能轻松在多个项目之间复用同一条规则，每次都需要重新配置 `workspace_id`，并根据每个项目的实际情况调整规则。

#### 人员信息静态

在现有 Rule 配置中，人员指派（如开发人员、测试人员、验证人员等）通常是写死在规则里的。

这意味着每次处理需求或修复缺陷时，系统会根据规则中的静态人员配置，自动把任务指派给特定人员。但对于多项目团队来说，这种方式灵活性不足。尤其当团队成员发生变化时，需要手动更新每个项目的人员配置。

比如，当 AI 处理一个缺陷时，默认会根据配置文件中的 `current_owner` 指派处理人，而这些人员信息是固定的，无法根据实际情况动态调整。

#### 跨项目灵活性不足

当前的 Rule 解决方案很难应对团队同时管理多个项目的情况。当一个项目需要与另一个项目共享规则时，我们需要手动在每个项目中配置并同步 Rule。

这不仅带来冗余操作，也增加了潜在错误。每次新项目启动时，都需要重新创建相同规则，无法实现真正的跨项目复用。

## 如何改进：引入 Skills 进行模块化管理

为了解决 Rule 的局限性，我们可以将原有 Rule 重构为 Skills，也就是模块化的标准作业程序（SOP）。

![模块化架构与配置](/img/tapd-skills/tapd-skills-architecture.png)

### 概念校准

- **Rule（`.cursorrules`）**：被动触发的全局上下文。AI 在每一轮对话都会读取，适合存放通用编码规范。
- **Skills（`.md` 文件）**：模块化的“技能库”。在 Cursor 中，可以将这些 Skill 文件存放在项目的 `.cursor/skills/`，或全局目录 `~/.cursor/skills/` 中。执行时，可以通过 `@filename` 显式激活，也可以在全局规则中告知 AI：“你是具备技能库的专家，必要时请主动检索技能文件夹。”

### 配置文件 + 模块化 Skills

建议将通用技能放在用户全局目录，而将项目特有配置留在仓库中：

```text
~/.cursor/skills/tapd/
├── tapd-hub/SKILL.md              # 技能路由与索引
├── tapd-workspace-config/SKILL.md # 配置解析引擎
├── tapd-today-plan/SKILL.md       # 今日任务读取
└── tapd-defect-update/SKILL.md    # 缺陷修复回写
```

项目配置文件示例：

```json
{
  "workspaceId": "",
  "projectLabel": "",
  "mcpServer": "user-mcp-server-tapd",
  "tapdSelf": {
    "owner": "开发负责人_示例ID"
  },
  "defectAfterFix": {
    "handoffOwner": "测试负责人_示例ID",
    "solutionNoteField": "custom_field_four",
    "changeStatusOnFix": true
  }
}
```

### 核心哲学：Skill 的本质是“意图的自动化”

在这里，我想强调一个观点：**Skills 应当通过自然语言描述让 AI 自己生成，而不是人工一行行编写。**

在我的实践中，我从不纠结 Skill 的语法。我只需要告诉 AI：

> 我需要一个处理 TAPD 缺陷回写的流程，它需要读取配置、检查状态，最后流转给测试。

然后让 AI 基于这个描述生成 `SKILL.md`。

为什么必须是自然语言？因为 Skill 的受众是 AI。AI 对自然语言的理解力，远超它对死板逻辑的执行力。当我们将业务 SOP 用自然语言模块化后，AI 就能在执行时表现出“理解力”，而不仅仅是“执行力”。这种方式让 Skill 具备了自我修复和适应环境的能力。

## Skills 使用指南

在 Cursor Chat 中，你不再需要输入复杂指令。通过 `@` 符号，就可以精准激活特定的自动化能力。

### 场景一：开始一天的开发

```text
@tapd-today-plan 帮我看看今天当前项目有哪些要做的？
```

AI 行为：

- 自动读取 `.cursor/tapd.project.json` 中的 `workspaceId`。
- 调用 MCP 获取指派给你的 Story 和 Bug。
- 按优先级排列输出。

### 场景二：修复 Bug 后的回写

```text
@tapd-defect-update 刚才的缺陷 ID 1000000 已经修好了，同步到 TAPD。
```

AI 行为：

1. 从配置中获取 `handoffOwner`，例如测试人员。
2. 将修复方案，也就是代码改动摘要，填入 `solutionNoteField`。
3. 自动执行 `update_bug`，将处理人流转给测试，并更新状态。

### 场景三：跨项目切换

当你切换到另一个仓库时，只需要确保该仓库下有 `.cursor/tapd.project.json`。同一个 `@tapd-defect-update` 就会自动操作另一个空间 ID，实现逻辑复用。

## 进阶：引入 Script 增强 Skills

为了让 Skills 更强大，我们可以引入 Script 能力。AI 不仅可以调用 MCP 接口，也可以执行本地脚本处理复杂逻辑。

比如可以扩展一个 `tapd-report-gen`：

- 执行路径规范：由于 AI 的当前工作目录（CWD）通常是项目根目录，所以 Skill 描述中必须指定脚本的绝对路径，例如 `python3 ~/.cursor/skills/scripts/git_log_parser.py`。
- Skill 描述更新：当用户要求生成报告时，调用位于全局目录下的 Python 脚本提取今日 Commit。AI 需要确保环境路径正确，避免因找不到脚本导致 `Command not found`。

这种方式可以把复杂的数据处理、报告生成、变更摘要等逻辑交给脚本，而让 Skill 负责“何时调用、如何串联、如何解释结果”。

## 深度实战：以 Skill 为桥梁的前端 TDD 闭环

目前，我正在本地环境中探索一个更复杂的自动化场景：如何利用 Skill 连通从需求到上线测试的全链路。

在这个实验中，我构建了一个名为 `tapd-story-tdd` 的 Skill。它不再是死板的全局约束（Rule），而是一座引导 AI 程序员跨越不同开发阶段的逻辑桥梁。

![高级 TDD 流程与工具链闭环](/img/tapd-skills/tapd-skills-tdd.png)

### 需求感知与 TDD 转换

当你对 AI 说“要 TDD”时，Skill 会引导 AI 从 TAPD 获取 Story 详情，并立刻切换到测试先行模式。

### 跨工具协同

Skill 像导航员一样，指引 AI 先写会失败的 Vitest/Jest 单测。在代码实现“转绿”后，再无缝衔接到 Playwright E2E 测试。

### 可视化验证

在 Skill 的指引下，AI 会主动在本地以 `--headed` 模式运行浏览器。你可以亲眼看到 AI 像真人一样操作页面、断言，并在失败时根据 Trace Log 自动进行“自愈”修复。

### 从开发到交付的跃迁

只有当所有由 Skill 定义的测试节点全部点亮，AI 才会认为该任务具备了上线测试条件。

### 核心思考：Rule 是红线，Skill 是桥梁

在我的体系中，两者分工非常明确：

- **Rule（`.cursorrules`）是“红线”**：它是底层的、被动的约束。比如必须遵守某套命名规范，禁止直接修改生产环境配置。无论 AI 在做什么，都不能踩线。
- **Skill（`.md`）是“桥梁”**：它是高层的、主动的 SOP。它负责告诉具备强大编码天赋的模型，如何优雅地把 TAPD 需求、代码逻辑和 Playwright 测试串联起来。

正如 `tapd-story-tdd` 案例：编码本身靠的是模型天赋，但如何让编码过程符合 TDD 规范、如何正确调用 Playwright、如何处理需求修复与新建需求的差异，这些流程上的衔接全部交由 Skill 导航。

这种“红线守底、桥梁通航”的模式，让 AI 在多项目协作中既不会乱跑，又能高效完成复杂的业务闭环。

## 总结与下一步

通过将 Rule 模块化为 Skills，我们实现了：

- **低成本复用**：新项目无需重新编写逻辑，只需准备一份 `tapd.project.json` 即可接入全套自动化。
- **动态感知**：AI 能够根据项目配置文件自动识别角色映射，而不是硬编码指派。
- **调用统一**：通过 `@tapd-xxx` 精准唤醒，减少全局 Rule 对 Token 的无效占用。

最后多说一句，我其实只是通过 TAPD 这个具体场景，为大家演示了一个 Skills 模块化落地的最小闭环。

重点不在于 TAPD 工具本身，而在于通过“Skill 导航”把那些琐碎流程规范化。未来的多项目协作，不再是我们为每个项目写一套规则，而是建立一套“技能母版”，让 AI 能够根据每个项目的 `project.json`，在自然语言的指引下，像经验丰富的老员工一样自动“悟出”该如何操作。
