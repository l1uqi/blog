> 经验声明：本文是 AI 编程基础概念系列的第七篇。前面讲了 LLM、Token、Context、Tool、MCP 和 Agent，这一篇讲 Skill。Skill 的重点不是让 AI 多一个按钮，而是让它按更稳定的方法做事。

## 先抓住这篇的模型

Skill 不是工具本身，而是一份**可复用的任务操作手册**。它告诉 AI：遇到某类任务时，应该按什么步骤推进、看哪些材料、注意哪些边界。

```text
一次任务里的临时经验
  ↓ 总结
稳定流程
  ↓ 写成 Skill
后续同类任务
  ↓ 按 Skill 执行
更少重复解释，更少遗漏步骤
```

可以这样区分几个概念：

| 概念 | 解决的问题 |
| --- | --- |
| Tool | AI 能做什么操作 |
| MCP | Tool 如何被标准化接入 |
| Agent | 如何围绕目标持续推进任务 |
| Skill | 一类任务应该怎么做 |
| Rule | 做事时哪些边界不能踩 |
| Context | 当前这次任务需要看什么 |

当你反复让 AI 做同一类任务时，会遇到一个很现实的问题：

每次都要重新解释规则。

比如你希望 AI 修 bug 时先复现、再定位、再最小修改、最后跑测试。

你希望它写文章时固定使用某种结构。

你希望它做代码审查时先找风险，而不是先夸代码。

你希望它处理 Excel 时先校验公式，再导出结果。

这些要求如果每次都手动输入，会很麻烦，也会浪费 token。

Skill 就是用来沉淀这类重复经验的。

## Skill 是什么

你可以把 Skill 理解成：

```text
让 AI 处理某类任务时使用的操作手册。
```

它通常会告诉 AI：

- 什么时候应该使用这个 Skill。
- 这个任务应该按什么步骤做。
- 哪些规则必须遵守。
- 哪些边界不能碰。
- 输出应该长什么样。
- 必要时可以调用哪些脚本或资源。

它不像 Tool 那样直接执行一个动作。

它更像公司的 SOP。

一个新人有电脑、有浏览器、有代码仓库，不代表他就知道怎么按团队流程修 bug。

AI 也一样。

Tool 给它能力。

Skill 给它方法。

## Skill 和 Tool 的区别

这两个词很容易混。

Tool 是能力。

Skill 是流程。

比如：

- 能运行测试，这是 Tool。
- 知道修 bug 时要先复现、再定位、再最小修改、最后验证，这是 Skill。

再比如：

- 能访问 TAPD，这是 Tool。
- 知道如何读取任务、分析需求、改代码、验证结果、回写状态，这是一套 Skill。

所以可以这样记：

```text
Tool 解决“能不能做”。
Skill 解决“应该怎么做”。
```

只有 Tool，没有 Skill，AI 可能会乱用能力。

只有 Skill，没有 Tool，AI 知道流程，但不一定能真正执行。

两者配合起来，AI 才更像一个靠谱的协作者。

## 为什么 Skill 能节省上下文

Skill 还有一个很重要的价值：节省 Context。

如果你每次都把完整流程贴给 AI，会占很多 token。

比如一套代码审查要求可能包括：

- 先找 bug 和回归风险。
- 不要把风格建议放在最前面。
- 每个问题要带文件和行号。
- 没有问题要明确说明。
- 最后再补充测试缺口。

这些规则如果每次都手动输入，很容易又长又乱。

如果沉淀成 Skill，就可以在任务匹配时按需加载。

也就是说，Skill 让复杂经验变成可复用的工作方法，而不是每次都塞进提问里。

这和前面讲的 Context 有关系：

**好的 Skill 会让 AI 在需要时读取正确规则，而不是一开始就背着所有规则干活。**

## 哪些内容适合做成 Skill

不是所有提示词都值得做成 Skill。

适合沉淀成 Skill 的，通常有几个特点：

- 经常重复。
- 有稳定流程。
- 有明确输出格式。
- 有容易踩坑的边界。
- 需要调用工具或脚本。
- 对质量稳定性要求高。

比如：

- 技术文章写作 Skill。
- 代码审查 Skill。
- Bug 修复 Skill。
- 数据分析 Skill。
- PPT 制作 Skill。
- 需求拆解 Skill。
- 测试报告 Skill。

这些任务不是一句话就能做好。

它们需要步骤、判断和经验。

这正是 Skill 的价值所在。

## Skill 让 AI 更像熟悉流程的同事

一个刚接入项目的 AI，即使模型很强，也不一定懂你的工作习惯。

你希望它：

- 改代码前先读相关文件。
- 不要随便重构。
- 修完必须跑测试。
- 输出时说明改了什么。
- 不要碰无关文件。
- 遇到敏感操作先确认。

这些都可以逐渐沉淀成 Skill、Rules 或项目说明。

当这些经验被结构化以后，AI 就不只是“听你这次怎么说”，而是能更稳定地按照你的方式工作。

这也是 AI 编程从“会聊天”走向“能协作”的关键。

## Skill 和 Rule 的关系

讲到这里，很容易出现一个疑问：

```text
Rule 不也是告诉 AI 怎么做吗？那 Rule 不就是 Skill 吗？
```

它们确实有重叠，但最好不要完全混成一个东西。

我更愿意这样区分：

```text
Skill 是一套做事流程。
Rule 是这套流程里必须遵守的约束。
```

比如“修一个 bug”可以是一套 Skill。

它会告诉 AI：

- 先复现问题。
- 再定位相关代码。
- 做最小修改。
- 跑测试验证。
- 最后说明影响范围。

但在这套 Skill 里面，可能会包含一些 Rule：

- 不要顺手重构无关模块。
- 支付状态字段不能直接改枚举。
- 改接口参数时必须同步更新类型定义。
- 涉及线上数据删除时必须先询问用户。

所以 Rule 可以出现在 Skill 里面。

但 Rule 也可以独立存在。

比如某个项目里有一条长期规则：

```text
所有 API 错误必须经过统一 errorHandler，不要在业务组件里直接 message.error。
```

这条规则不只适用于“修 bug”这个 Skill，也适用于写新功能、做重构、补测试。它更像项目级边界。

因此可以简单记：

```text
Skill 关心任务怎么推进。
Rule 关心哪些事情不能做错。
```

下一篇单独讲 Rules，就是因为 AI 编程里很多问题不是“AI 不会做流程”，而是“AI 不知道这个项目有哪些不能踩的边界”。

## 把 7 个词连起来

到这里，LLM、Token、Context、Tool、MCP、Agent 和 Skill 可以串成一条线：

```text
LLM 负责理解和生成。
Token 是模型处理文字的基本颗粒。
Context 是这次摆在模型面前的材料。
Tool 是 AI 可以调用的外部能力。
MCP 是工具和数据接入 AI 的标准协议。
Agent 是围绕目标持续推进任务的工作单元。
Skill 是某类任务的操作手册。
```

这几个词不是孤立概念。

它们组合在一起，才构成真实的 AI 编程协作。

LLM 再强，也需要合适的 Context。

Context 再好，也会受 Token 限制。

Tool 能让 AI 做事，但需要 MCP 这样的标准方式接入更多系统。

Agent 把目标、推理、工具调用和反馈组织成连续行动。

Skill 则告诉 AI：在具体任务里，应该按什么方法使用这些能力。

## 总结

Skill 的核心不是“多一个功能”，而是“沉淀一种可复用的做事方法”。

可以先记住这几句话：

- Skill 是某类任务的操作手册。
- Tool 是能力，Skill 是流程。
- Rule 可以是 Skill 里的一部分，但 Rule 不等于 Skill。
- Skill 能减少重复提示，节省上下文。
- 好的 Skill 会包含步骤、规则、边界和输出要求。
- AI 编程越深入，越需要把经验沉淀成可复用工作流。

理解完这 7 个词，再看 Rules、Context、Memory、Project Map，就会清晰很多。

它们其实都在回答同一个问题：

**怎么让一个聪明但不熟悉项目的 AI，逐渐变成一个真正懂项目、懂流程、懂边界的协作对象。**
