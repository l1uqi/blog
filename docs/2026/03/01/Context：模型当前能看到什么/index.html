Context：模型当前能看到什么

2026-05-06 · 5 min · 1.4k words · AI

经验声明：本文是 AI 编程基础概念系列的第三篇。上一篇讲 Token，这一篇讲 Context。很多 AI 编程问题，本质不是模型不够聪明，而是它当前看到的材料不对。

先抓住这篇的模型

Context 不是“项目里客观存在的所有资料”，而是模型这一次回答时真正看得到的东西。

可以把它理解成一张临时工作台：

所以好的提问，本质上不是把 prompt 写得更玄，而是把 Context 组织得更准。

Context 状态 AI 的表现
缺少关键文件 容易写出看似合理但接不上项目的代码
只有结论，没有背景 容易误判需求动机
材料太多且无重点 容易抓错主线
目标、约束、证据都清楚 更像在真实项目里协作

Context 翻译成中文是上下文。

但在 AI 编程里，这个词很容易被误解。

很多人以为 Context 是“AI 知道的一切”。

不是。

更准确地说：

模型每次回答，不是凭空从一个完整记忆库里拿东西。

它会基于当前请求里被放进去的内容进行推理和生成。

Context 里通常有什么

在 AI 编程场景里，Context 可能包括：

  • 你当前的问题。
  • 前面的对话历史。
  • 系统提示词。
  • 项目规则。
  • 当前打开的代码文件。
  • 工具读取到的文件内容。
  • 终端输出。
  • 测试失败信息。
  • 报错日志。
  • 相关文档。

这些内容共同决定了模型这次“知道什么”。

如果你让 AI 修一个 bug，但没有给它报错，也没有让它读取相关代码，它就只能根据经验猜。

如果你给它刚好相关的错误日志、调用链、文件和限制条件，它就更像一个真正进入现场的协作者。

Context 像一张工作台

我喜欢把 Context 想成一张工作台。

工作台太空，AI 没材料。

你只说：

模型不知道是哪个页面、哪个接口、哪个文件、什么错误，只能泛泛而谈。

工作台太乱，AI 抓不住重点。

你把整个项目文档、几十个文件、历史聊天、所有规则都塞进去，模型虽然看到了很多东西，但真正关键的信息可能被淹没。

好的 Context 不是大，而是准。

比如：

这才是一个更好的工作台。

任务、现象、材料、边界都有了。

Context 不是 Memory

Context 和 Memory 也很容易混。

Context 是这一次模型当前能看到什么。

Memory 是长期保存、未来可以按需取回的背景。

可以这样理解：

仓库里可能有很多资料，但如果这次没有取出来放到桌面上，模型就不一定能用上。

这也是为什么有时你会觉得 AI “忘了之前说过的话”。

可能不是它故意忘，而是那段信息没有进入当前上下文，或者在上下文压缩时被省略了。

AI 编程最需要什么 Context

不同任务需要的 Context 不一样。

修 bug 时，最重要的通常是：

  • 复现步骤。
  • 错误日志。
  • 相关文件。
  • 最近改动。
  • 测试输出。

写新功能时，最重要的通常是：

  • 需求目标。
  • 现有类似实现。
  • 数据结构。
  • 接口约定。
  • UI 或交互边界。

做重构时，最重要的通常是：

  • 重构范围。
  • 不允许改变的行为。
  • 调用方。
  • 测试覆盖。
  • 发布风险。

所以，给 AI Context 的关键不是“把所有东西都给它”，而是先判断这次任务真正需要哪些材料。

好的提问就是在组织 Context

很多所谓 prompt 技巧，本质上都是在组织 Context。

比如你可以这样问：

这段话做了几件事：

  • 说明任务目标。
  • 给出现象。
  • 给出关键日志。
  • 指定相关文件。
  • 设置修改边界。
  • 规定输出顺序。

模型拿到这样的 Context，通常会比只看到“登录失败，帮我修”稳得多。

总结

Context 决定了 AI 当前能依据什么来判断。

如果 Context 太少，AI 会猜。

如果 Context 太乱，AI 会被干扰。

如果 Context 准确，AI 才更可能写出符合项目实际情况的代码。

可以先记住这几句话：

  • Context 是当前任务里模型能看到的材料。
  • Context 不是 AI 知道的一切。
  • Context 和 Memory 不是一回事。
  • 好的 Context 不是大，而是准。
  • 给 AI 提问，本质上是在帮它组织工作台。
