MCP：工具接入 AI 的标准接口

2026-05-06 · 4 min · 1.2k words · AI

经验声明：本文是 AI 编程基础概念系列的第五篇。上一篇讲 Tool，这一篇讲 MCP。MCP 不是某个神奇工具，而是一套让 AI 更容易连接外部世界的协议。

当 AI 需要使用外部工具时，很快会遇到一个工程问题：

工具太多，平台也太多。

文件系统、数据库、浏览器、GitHub、TAPD、飞书、Notion、Jira、公司内部系统，每个系统都有自己的接口和权限模型。

如果每个 AI 应用都要为每个工具单独适配一遍，整个生态会非常碎。

MCP 就是为了解决这类问题出现的。

MCP 是什么

MCP，全称 Model Context Protocol，模型上下文协议。

你可以先把它理解成：

更大白话一点：

比如一个数据库查询能力可以通过 MCP 暴露出来。

一个 GitHub issue 查询能力也可以通过 MCP 暴露出来。

一个公司内部工单系统也可以通过 MCP 暴露出来。

AI 应用不用为每个系统从零设计一套接入方式，而是按 MCP 的规范发现和调用这些能力。

MCP 里有哪些角色

可以先粗略理解几个角色。

Host 是用户正在使用的 AI 应用。

比如 IDE、聊天应用、AI 编程工具。

Client 是 Host 里负责连接 MCP Server 的部分。

它负责和 Server 通信。

Server 是暴露具体能力的一端。

比如文件系统 Server、数据库 Server、GitHub Server、浏览器 Server。

Server 可以暴露几类东西：

  • Tool：可以执行的动作。
  • Resource：可以读取的数据。
  • Prompt：可以复用的提示模板。

这些概念不用一开始背得很细。

新人先抓住主线就够了：

MCP 让 AI 应用可以用更统一的方式发现和使用外部能力。

MCP 不是 Tool 本身

很多人会把 MCP 和 Tool 混成一个东西。

它们相关，但不是一回事。

Tool 是具体能做的事。

比如：

  • 查询数据库。
  • 搜索代码。
  • 创建 issue。
  • 读取文件。
  • 打开浏览器。

MCP 是让这些能力接入 AI 的协议。

比如你写了一个 MCP Server，里面暴露了一个 search_ticket 工具。

AI 应用通过 MCP 知道这个工具叫什么、需要什么参数、会返回什么结果，然后才能调用它。

所以 MCP 更像接口规范，不是某个具体动作。

为什么 MCP 对 AI 编程重要

AI 编程不是只写代码。

真实工作里，代码往往和很多系统连在一起：

  • 需求在 TAPD 或 Jira。
  • 代码在 GitHub 或 GitLab。
  • 文档在 Notion 或飞书。
  • 数据在数据库。
  • 页面要在浏览器里验证。
  • 线上问题可能在日志系统里。

如果 AI 只能看到你手动贴的一点代码，它做事就很受限。

如果这些系统都能通过标准协议接进来，AI 就可以更自然地获取信息、执行动作和验证结果。

这就是 MCP 的价值。

它不是让模型本身突然变聪明。

它是让模型更容易连接真实工作现场。

MCP 更像基础设施

对新人来说，不需要一开始就会写 MCP Server。

更重要的是理解它解决的问题。

当你听到别人说“接一个 MCP”，通常不是说换一个模型，而是说：

比如：

  • 接文件系统 MCP，让 AI 能读写指定目录。
  • 接数据库 MCP，让 AI 能查结构和数据。
  • 接浏览器 MCP，让 AI 能打开页面检查结果。
  • 接内部系统 MCP，让 AI 能读取公司业务信息。

这些能力最终都会变成 AI 可以使用的上下文和工具。

总结

MCP 的重点不是“神奇”，而是“标准化连接”。

可以先记住这几句话：

  • MCP 是 Model Context Protocol。
  • MCP 是一种协议，不是某个具体工具。
  • Tool 是具体能力，MCP 是能力接入 AI 的标准方式。
  • MCP Server 可以暴露 Tool、Resource 和 Prompt。
  • MCP 让 AI 更容易连接文件、数据库、浏览器和业务系统。

下一篇讲 Skill。

如果说 MCP 解决的是“外部能力怎么接进来”，那么 Skill 解决的是“接进来之后，AI 应该按什么流程做事”。
