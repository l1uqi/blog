为什么模型 Context 决定 AI 编程效果

2026-05-06 · 8 min · 2.6k words · AI

经验声明：本文是 AI 编程协作系列的第四篇。上一篇讲 Rules，这一篇单独讲 Context。因为模型能不能写对代码，很多时候不是能力问题，而是它当前到底看到了什么。

先抓住这篇的模型

这篇文章讲的是 AI 编程里一个经常被低估的判断：模型不是在“理解你的项目”，而是在基于当前可见 Context 做推理。

同一个模型，在不同 Context 下会像两个完全不同的助手：

Context 质量 模型表现
只给一句需求 容易给通用方案
给需求和当前文件 能改局部，但可能忽略调用方
给需求、相关文件、错误日志、约束 更可能做出贴合项目的修改
给一堆无关文档 看似信息充分，实际注意力被稀释

很多人评价 AI 编程工具时，会说一句话：

这句话很多时候是对的。

但更准确地说，不是模型完全不懂，而是它当前这一次任务的 Context 不够好。

模型不像人类同事。人类同事会记得昨天开会讲过什么，会知道这个模块谁改过，会记住上次线上问题的结论。AI 如果没有被提供这些信息，或者没有工具帮它检索这些信息，它就只能根据当前窗口里能看到的内容推理。

所以 Context 决定了一个很基础的问题：

模型这次到底是在“看着项目写代码”，还是在“凭经验猜代码”。

Context 不是资料越多越好

很多人会误以为，Context 就是把更多资料塞给 AI。

比如：

  • 把整个项目说明贴进去。
  • 把所有 Rules 都塞进去。
  • 把几十个相关文件一次性打开。
  • 把历史聊天记录全部丢进去。

这看起来是在帮 AI，实际经常会让效果变差。

因为模型的注意力不是无限的。

上下文越多，噪音也越多。真正关键的错误日志、类型定义、调用链，反而可能被大量无关内容冲淡。

所以我更愿意把 Context 理解成一个工作台。

工作台太空，AI 没工具。

工作台太乱，AI 找不到重点。

好的 Context 不是“大”，而是“准”。

如果公司里有一个拥有完整上下文的人

可以换一个更生活化的例子。

假设一家公司里有一个员工。

他从公司成立第一天就在。

公司为什么做这个产品，他知道。

第一批客户怎么来的，他知道。

哪些功能做过又删掉，他知道。

哪些技术债是当年为了赶上线留下的，他知道。

销售、产品、研发、测试、客服、财务之间怎么协作，他也知道。

甚至每一次重大决策为什么发生、后来造成了什么结果、谁踩过什么坑，他都知道。

那这个人是不是可以帮公司做任何决策？

我的答案是：他不一定能替所有人做决策，但他一定会显著提高几乎所有决策的质量。

因为决策不只需要信息。

决策还需要目标、责任、风险偏好和价值取舍。

比如公司要不要砍掉一个老功能，不只是看历史数据，还要看当前战略、客户承诺、团队资源和未来方向。

这些不能简单交给“知道最多的人”自动决定。

但一个拥有完整上下文的人，会非常接近公司里的超级参谋。

他可以提醒你：

  • 这个方案三年前试过，失败原因不是技术，而是销售流程没跟上。
  • 这个客户现在看起来很小，但曾经推动过一个关键行业案例。
  • 这个字段不能随便删，因为还有一批老版本客户端依赖它。
  • 这个需求表面是产品问题，背后其实是客服每天重复处理的成本。
  • 这个技术方案短期快，但会让下个季度的迁移更痛。

这就是 Context 的价值。

很多错误决策，并不是因为人不聪明，而是因为只拿到了局部上下文。

产品只看到用户需求。

研发只看到技术实现。

销售只看到客户压力。

客服只看到问题反馈。

财务只看到成本数字。

每个人都看到了真实的一部分，但没有人看到完整关系。

AI 也是一样。

当我们说模型需要更好的 Context，本质上不是让它背更多资料，而是让它在当前任务里，尽可能接近那个“从公司成立第一天就在场的人”。

它知道历史，知道约束，知道关联，知道过去踩过的坑，也知道当前任务真正不能碰的边界。

这样的 AI 才不只是一个代码生成器，而更像一个懂项目的协作对象。

模型只能基于当前可见信息推理

AI 编程最容易被误解的一点是：模型看起来很聪明，所以我们会默认它知道很多项目背景。

但真实情况是，它在一次任务里主要依赖三类信息：

  • 模型参数里学到的通用知识。
  • 当前上下文窗口里的内容。
  • 工具临时读取或检索到的信息。

通用知识可以让它知道 React、Vue、TypeScript、Node 怎么写。

但通用知识不会告诉它：

  • 你们项目为什么不能改某个字段。
  • 某个目录是不是已经废弃。
  • 某个组件是不是被十几个页面复用。
  • 某个接口错误是不是必须走统一处理。
  • 某个状态值是不是为了兼容旧版本保留下来的。

这些都是项目 Context。

如果 Context 没给到，AI 就只能用通用经验补空白。

而真实业务代码里，最容易出问题的地方，往往就是这些通用经验覆盖不了的空白。

Context 缺失会造成什么问题

Context 缺失时，AI 通常不会直接说“我不知道”。

它更可能做三件事。

第一，生成看起来合理但不符合项目的代码

比如项目明明有统一请求层，它却在组件里直接 try/catch。

代码语法没问题，甚至看起来还挺完整，但项目规范错了。

第二，重复造轮子

它不知道项目里已经有工具函数，就会新写一个。

它不知道已有组件模式，就会新建一个不一致的实现。

这种问题短期看不严重，长期会让项目越来越碎。

第三，误判影响范围

它只看到当前文件，就以为改动只影响当前页面。

但真实项目里，一个公共组件、一个 request 封装、一个权限判断，可能影响很多地方。

如果 Context 没包含调用方和模块关系，AI 就很难判断风险。

好 Context 应该包含什么

我觉得一次 AI 编程任务，比较理想的 Context 至少包括几类信息。

当前任务

它要知道你到底想做什么。

比如是修 bug、新增需求、重构、排查问题，还是只做代码解释。

任务类型不同，需要的 Context 完全不同。

相关代码

不是整个项目，而是和当前任务相关的代码。

比如：

  • 当前文件。
  • 调用方。
  • 被调用的 service。
  • 类型定义。
  • 测试文件。
  • 相似实现。

项目规则

这里只需要和当前任务相关的规则。

比如改接口时，需要接口错误处理规则；改组件时，需要组件规范；改测试时，需要测试约定。

运行反馈

包括：

  • 错误日志。
  • TypeScript 报错。
  • 单测输出。
  • 浏览器截图。
  • 构建结果。

这些反馈能让 AI 从“猜”变成“验证后再改”。

历史背景

这部分不一定每次都需要。

但如果任务涉及历史兼容、业务字段、线上问题、用户偏好，就需要从 Memory 或文档里取回来。

Context 和 Rules 的关系

Rules 不是 Context 的全部。

Rules 是长期稳定的约束。

Context 是当前任务需要的工作材料。

它们非常重要，但不应该永远塞在 Rule 里。

Context 和 Memory 的区别

Context 是模型当前能看到的内容。

Memory 是可以长期保存、未来按需取回的内容。

两者关系可以这样理解：

如果所有材料都放桌面上，桌面会乱。

如果仓库里没有材料，下一次又要重新找。

所以合理的做法是：

  • Rules 常驻少量红线。
  • Project Map 告诉 AI 去哪里找。
  • Memory 保存长期背景。
  • Context 只放当前任务真正需要的信息。

这就是后面要讲渐进式披露的原因。

总结

模型 Context 的重要性，常常被低估。

很多时候，AI 不是不会写代码，而是它没有看到该看的东西。

Context 太少，AI 会瞎猜。

Context 太多，AI 会迷路。

真正有效的 AI 编程，不是无限堆资料，而是让模型在每一步都看到刚好需要的信息。
