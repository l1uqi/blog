AI 编程新人先懂这几个词：LLM、Token、Context、Tool、MCP 和 Skill

2026-05-06 · 8 min · 2.4k words · AI

经验声明：本文是 AI 编程协作系列的第二篇。上一篇讲为什么很多人用不好 AI 编程工具，这一篇先不讲复杂方法，只把几个最容易混在一起的基础词说清楚：LLM、Token、Context、Tool、MCP 和 Skill。

LLM 是会理解和生成文字的大脑

LLM 是 Large Language Model，大语言模型。

你可以先把它理解成一个很会读文字、接文字、写文字的大脑。

它看了前面的内容，然后判断后面应该怎么回答。

为什么它能写代码？

因为它训练时见过大量代码、文档、文章、错误日志、问答和解释。

所以它不只是会聊天，还能：

  • 写函数。
  • 解释报错。
  • 总结需求。
  • 推断调用链。
  • 给出修改方案。
  • 帮你整理文档。

但这里有一个关键点：

LLM 再聪明，也不是天然住在你的项目里。

它不知道你们公司的业务历史，不知道这个字段为什么不能删，不知道某个接口为什么要兼容旧版本。

这些东西要靠 Context、Tool、Memory、Rules 这些机制补给它。

所以不要把 LLM 想成“全知全能的人”。

更准确地说，它像一个通用能力很强的新同事。

它很聪明，但刚进项目时，并不知道你们项目里的那些旧账、边界和默认规矩。

Token 是模型眼里的文字颗粒

人看文字，通常是按字、词、句子来理解。

模型看文字，会先把文字切成 token。

你可以把 token 理解成“模型吃进去的文字颗粒”。

比如这句话：

在人眼里，它就是一句话。

但在模型眼里，它会先被拆成一小块一小块的 token。中文、英文、空格、标点、代码符号，都可能被切成不同的 token。

你可以在网上找 tokenizer 工具试一下。

它通常可以做两件事：

  • 文字 -> token：输入一段文字，看它被拆成哪些 token。
  • token 或 token ID -> 文字片段：看某个 token 对应原文里的哪一小块。

这个过程看起来有点底层，但它和 AI 使用体验关系很大。

因为模型的上下文长度，不是按“多少个汉字”算，也不是按“多少页文档”算，而是按 token 算。

你贴一大段日志，它会占 token。

你塞很多项目规则，它也会占 token。

你让 AI 一次性读十几个文件，它还是会占 token。

这就是为什么有时候你明明觉得“我也没给多少东西”，但模型已经开始丢重点了。

不是它故意不看。

而是桌子就那么大，token 太多，真正关键的信息可能被挤到边缘。

Context 是这次摆在模型面前的材料

Context 翻译成中文就是上下文。

但这个词很容易被误解。

Context 不是“AI 知道的一切”。

Context 是这一次对话、这一次任务里，模型当前能看到的内容。

比如你让 AI 修一个 bug，它能看到的 Context 可能包括：

  • 你写的需求描述。
  • 当前打开的代码文件。
  • 报错日志。
  • 相关测试输出。
  • 项目 Rules。
  • 工具读取到的文件内容。
  • 前面几轮对话。

这些才是它这次真正能用来推理的材料。

我喜欢把 Context 想成一张工作台。

工作台上没有材料，AI 只能猜。

工作台上材料太乱，AI 会抓不住重点。

工作台上刚好放了任务、错误、相关代码、项目规则和验证结果，AI 才比较容易做对。

所以 Context 不是越多越好。

好的 Context 不是大，而是准。

Tool 是 AI 可以伸出去的手

如果没有 Tool，AI 就只能靠你贴给它的内容回答。

你没贴代码，它就看不到代码。

你没贴日志，它就看不到日志。

你没贴测试结果，它就不知道刚才改完有没有问题。

有了 Tool 之后，AI 可以主动去做一些事。

比如：

  • 搜索代码。
  • 读取文件。
  • 运行测试。
  • 查看终端输出。
  • 打开网页。
  • 查询数据库。
  • 调用某个业务系统接口。

这时 AI 就不只是一个聊天窗口。

它开始能参与真实工作。

用大白话说：

所以 Tool 很重要。

没有 Tool，AI 很容易停留在“你问一句，它答一句”。

有了 Tool，它才可能自己查证、自己验证、自己迭代。

MCP 是让工具接进来的标准接口

工具多了以后，会出现一个问题：

每个工具都有自己的接入方式。

文件系统有文件系统的方式。

数据库有数据库的方式。

浏览器有浏览器的方式。

GitHub、TAPD、飞书、Notion、Jira，又各有各的方式。

如果每个工具都单独适配一遍，AI 工具生态会非常碎。

MCP 可以先粗略理解成一种标准接口。

它像一个插座规范。

只要工具按这个规范接进来，AI 就能用比较统一的方式发现工具、读取资源、调用能力。

所以 MCP 不是某一个具体工具。

它更像“让 AI 连接工具的一套协议”。

你可以把它想成：

比如一个 TAPD 工具可以通过 MCP 接进来。

一个数据库查询工具也可以通过 MCP 接进来。

AI 不需要知道每个系统背后的所有细节，它只需要按 MCP 暴露出来的方式去调用。

这就是 MCP 的价值：让 AI 更容易连接外部世界。

Skill 是做某类任务的操作手册

Tool 解决的是“能不能做”。

Skill 解决的是“应该怎么做”。

这两个很容易混。

比如 AI 能调用命令行，这是 Tool。

但“修一个 bug 时，应该先复现、再定位、再最小修改、再跑测试、最后说明影响范围”，这是 Skill。

再比如 AI 能访问 TAPD，这是 Tool。

但“读取今日任务、分析需求、改代码、跑验证、回写 TAPD 状态”，这是一套 Skill。

所以 Skill 更像公司的 SOP。

它不是能力本身，而是把能力组织成一个稳定流程。

一个新人有电脑、有浏览器、有代码仓库，不代表他就知道怎么按团队流程修 bug。

AI 也一样。

Tool 只是给它能力。

Skill 才告诉它在某类场景下应该按什么顺序使用这些能力。

把这些词放到一次真实任务里看

假设你对 AI 说：

这时候几个概念会一起出现。

LLM 负责理解你的话：你要排查一个保存失败的问题。

Context 是它当前能看到的材料：你的描述、当前代码、错误日志、相关规则。

Token 是这些材料进入模型时被切成的文字颗粒，决定它们占多少上下文空间。

Tool 让它可以去搜索 profile、读取相关 service、运行测试、查看报错。

MCP 可能负责把 GitHub、TAPD、数据库、浏览器这些外部能力接进来。

Skill 则告诉它应该怎么排查：先复现，再定位调用链，再看接口返回，再做最小修改，最后验证。

这时 AI 编程就不再是单纯聊天。

几个常见误解

Token 不是字数

尤其中文场景里，不要简单把 token 等同于汉字数。

它是模型自己的切分方式。

所以判断上下文大小时，不能只看“我贴了多少行”，还要意识到这些内容都会占 token。

Context 不是 Memory

Context 是这次模型当前能看到什么。

Memory 是长期保存、未来可以按需取回的背景。

可以这样理解：

Tool 不是 Skill

Tool 是能力。

Skill 是流程。

AI 能跑测试，不代表它知道什么时候该跑、跑哪个、失败后怎么处理。

这就需要 Skill。

MCP 不是某个神奇产品

MCP 更像协议或接口规范。

它的价值不是“自己完成任务”，而是让各种工具更容易被 AI 调用。

总结

如果你刚开始接触 AI 编程，可以先记住这几句话：

  • LLM 是大脑。
  • Token 是模型能读懂的文字颗粒。
  • Context 是这次摆在模型面前的材料。
  • Tool 是 AI 可以调用的外部能力。
  • MCP 是工具接入 AI 的标准接口。
  • Skill 是某类任务的操作手册。

这些词不是孤立的。

它们组合在一起，才构成真实的 AI 编程协作。

后面讲 Rules、Context、渐进式披露、Project Map、Memory，其实都在回答同一个问题：

怎么让一个聪明但不熟悉项目的 AI，逐渐变成一个真正懂项目、懂流程、懂边界的协作对象。
